# 面试项目介绍讲稿（约 2 分钟，可直接背诵）

## 一、项目背景与要解决的问题

我做的是一个模拟电商平台的 AI 智能客服系统。最开始只有关键词匹配：顾客必须输入「蓝牙耳机」四个字才能查到价格。另一个极端是直接把问题丢给大模型，模型可能随口编一个价格——电商场景里价格、库存编错了是事故。

所以核心问题是：**让客服既能听懂自然语言，又保证回答的数据准确、可追溯。**

## 二、整体架构

系统分五层：数据层是本地 JSON（3 个商品、7 条 FAQ、3 条种子订单 + 运行时状态文件）；检索层是轻量 RAG（16 个知识块的向量索引）；工具层是 12 个 Python 函数，负责真正查数据和办业务；Agent 层是 Function Calling 工作循环；展示层是 Streamlit 网页。

一次对话的数据流：顾客提问 → 大模型判断意图并说「调用 check_stock，参数 name=蓝牙耳机」→ 程序执行函数拿到 `{"stock": 50}` → 结果以 `role=tool` 回传 → 模型据此生成「目前库存 50 件」。也就是说价格不是模型想出来的，是工具查出来的。开放式问题（比如「有防水面料的商品吗」）则先走 RAG 语义检索，把命中的知识片段交给模型作答。

## 三、技术选型与理由

- **DeepSeek + OpenAI SDK**：官方接口兼容 OpenAI 格式，用 SDK 调用简洁，`deepseek-chat` 成本低。
- **不用 LangChain**：一个 Agent、12 个工具、一个循环，原生 Function Calling 一百多行就能写清楚，每一步 messages 都可见，调试和讲解成本最低。
- **RAG 用 TF-IDF 而不是神经网络 Embedding**：DeepSeek 官方没有 Embedding 接口，本地也没有 GPU，所以用零依赖的中文 bi-gram + TF-IDF 稀疏向量 + 余弦相似度实现完整检索链路——查询和文档都转成向量算夹角，是真实向量检索而不是关键词匹配。16 个文档块暴力计算就够，不必上 FAISS。**向量数据库和神经网络 Embedding 当前版本没有用**，是未来方向。
- **职责分离**：价格、库存、订单会随下单变化，属于结构化实时字段，走工具查询；规格、描述、FAQ 是静态文本，走 RAG。RAG 文档里故意不写库存，避免检索到过期数据。
- **密钥安全**：API Key 只从环境变量读取，代码、日志、文档里都没有，`.gitignore` 排除了 `.env`、`.venv`、`state.json`。

## 四、核心功能

商品/价格/实时库存/规格查询、FAQ 售后问答、按预算推荐、开放式问题语义检索、多轮对话、网页聊天；以及有状态的模拟业务：下单扣库存并生成订单、订单查询、物流跟踪、退款进度、售后申请状态机、转人工。所有订单数据明确标注为模拟演示数据。网页侧边栏能看到 Agent 每一轮的「决策 → 参数 → 执行结果」、RAG 命中片段与实时库存。

## 五、技术难点与解决方案

1. **防止编造数据**：System Prompt 要求涉及价格库存必须先调工具、知识库没有就明说；工具统一返回 `success` 字段，失败时如实说明并引导转人工。RAG 还加了相似度阈值拒答（0.28，由 22 条问答集标定），无关问题直接返回空上下文，模型不许自由发挥。
2. **RAG 的两个真实问题**：一是「问保温多久」时含答案的规格切片分数偏低会被过滤，我加了**父文档扩展**——命中某商品后把该商品其余切片一起带入；二是「什么时候发货」匹配不到键为「物流」的 FAQ，我给 FAQ 加了**混合检索**：精确关键词未命中就降级到语义检索兜底。
3. **有状态业务的数据一致性**：下单会真实扣库存，所以 Prompt 明确要求价格/库存每次都重新调工具，不能沿用历史对话里的旧值。评测第一轮就抓到了这个 bug（追问库存时模型复用了旧数值），修复后重测通过。
4. **工具调用不崩溃**：`execute_tool` 统一拦截未知工具、参数错误、执行异常；Agent 循环最多 3 轮；API 设 30 秒超时，402 余额不足等错误统一兜底。
5. **多轮对话与长记忆**：大模型本身没有记忆，每次都要把历史重新传进去。`memory.py` 按用户隔离、只保留最近 10 轮；超过 12 条时让模型把最旧 8 条压缩成滚动摘要作为长期记忆，摘要失败则降级为截断，不影响主流程。
6. **Windows 环境与界面 bug**：Spyder 自带 runtime 没有 pip，改用独立 venv + `spyder-kernels`；GBK 编码报错统一重配置 UTF-8；Streamlit 按钮点击后延迟一轮显示，补 `st.rerun()` 并写了 AppTest 回归测试。

## 六、项目成果

- 从关键词原型迭代到 12 工具 + RAG + 有状态业务的完整 Agent，代码按模块分层。
- 建立 22 条标准问答集自动评测：首轮 19/22，定位并修复 3 个真实缺陷（Prompt 区分规则咨询与业务办理、库存强制重查、FAQ 语义兜底），最终 **22/22 通过**；另有 6 组回归测试共 **76 项全部通过**。
- 评测报告、README、架构与求职材料完整；API 开发与测试累计成本约 0.2 元。
- 评测指标口径如实说明：样本仅 22 条、关键词比对、模型有随机性，**不代表生产环境准确率**。

## 七、未来优化方向

商品规模扩大后改用神经网络 Embedding + FAISS/Chroma；订单与会话写入 SQLite 支持多进程；扩大人工标注评测集替代关键词比对；增加 API 重试、限流、成本核算与 Docker 部署；在合法授权前提下接入真实平台接口。

## 八、一句话收尾

> 这个项目让我理解了 Agent 和聊天机器人的区别：不是模型更会说话，而是模型学会了「不知道就先去查、查完老实按结果回答」，并且系统会用评测集反过来验证它到底有没有做到。
