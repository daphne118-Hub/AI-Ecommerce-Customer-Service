# 项目面试问答（40 题）

> 原则：所有答案与项目实际代码一致。**RAG 已实现，但用的是 TF-IDF 稀疏向量；神经网络 Embedding、向量数据库、LangChain、真实平台 API 均未使用**，答案里都明确区分，不要背成已实现。
> 评测指标为 22 条演示样本的实测值，不代表生产环境准确率。

---

## 一、Python 基础

**Q1：为什么项目要用虚拟环境 `.venv`？**
A：把项目依赖隔离在单独的 Python 环境里，不污染系统 Python，也不会和其他项目的包版本冲突。我最初想在 Spyder 自带的 `spyder-runtime` 里装 `openai`，但它没有 pip 且是 Spyder 内部专用环境，官方不建议动，所以用 `D:\python\python.exe -m venv .venv` 建了独立环境，再在 Spyder 首选项里把解释器指过去，并安装 `spyder-kernels` 保证兼容。

**Q2：`import` 是怎么找到 `knowledge.py` 的？**
A：Python 会按 `sys.path` 顺序查找，当前脚本所在目录优先级很高，所以 `app.py` 里 `import knowledge` 能直接找到同目录模块。测试脚本在 `tests/` 子目录，我在测试文件开头用 `sys.path.insert(0, 项目根目录)` 保证导入成功。

**Q3：JSON 文件和 Python 字典是什么关系？为什么知识库用 JSON？**
A：`json.load()` 把 JSON 文件读成字典，`json.dumps()` 把字典转成 JSON 字符串。知识库用 JSON 是为了**数据与代码分离**：以后加商品只改 `data/products.json`，不用动查询逻辑。`knowledge.py` 启动时加载一次到模块变量 `products`、`faq`。

**Q4：`memory.py` 里为什么用类而不是全局变量？**
A：类可以把「数据」（history 列表）和「操作」（add/clear/get_messages）封装在一起，并且能创建多个独立实例。`MemoryManager` 用字典按 `user_id` 存不同 `ConversationMemory` 实例，实现用户之间的会话隔离。

**Q5：`try/except` 在项目里用在哪些地方？**
A：至少 5 处：`llm_client.chat()` 拦截所有 API 异常；`tools.execute_tool()` 拦截未知工具、参数错误和执行异常；`agent._call_llm()` 拦截模型调用失败；`agent.run()` 里解析 `tool_call.function.arguments` 时拦截 JSON 解析错误；`app.py` 里 stdout 重配置也做了保护。

**Q6：`**products[name]` 这种星号语法是什么？**
A：字典解包。`search_product()` 里 `{"name": name, **products[name]}` 把商品的所有字段（price、stock、specs…）合并进新字典，避免一个个手写字段。

## 二、API 接入与密钥安全

**Q7：DeepSeek 是怎么调用的？用哪个地址和模型？**
A：用 `openai.OpenAI(api_key=..., base_url="https://api.deepseek.com")` 创建客户端，因为 DeepSeek 官方接口兼容 OpenAI 格式。模型是 `deepseek-chat`（`config.MODEL_NAME`），调用 `client.chat.completions.create()`，参数有 `messages`、`tools`、`max_tokens=500`、`temperature=0.3`、`timeout=30`。

**Q8：API Key 怎么管理？**
A：只在 `config.py` 里用 `os.getenv("DEEPSEEK_API_KEY")` 从环境变量读取，绝不写进源码、日志或文档；`.gitignore` 排除了 `.env`、`*.key`、`.venv/`；`test_api.py` 只打印「读取成功」，不打印密钥内容。发现 402 之外的鉴权问题时，会提示去平台撤销并重新生成。

**Q9：遇到 `402 Insufficient Balance` 你怎么处理的？**
A：这是账户余额不足，不是代码问题。当时 `test_api.py` 前两步（密钥读取、客户端创建）都通过、网络也通，只有模型调用返回 402，所以判断为账户层面问题，提示用户去平台充值后重跑，充值后测试通过。这体现了「分层验证」的排错思路。

**Q10：为什么要设 `timeout=30` 和 `max_tokens=500`？**
A：超时防止网络异常时程序无限卡死；限制最大输出长度既能控制单次费用，也符合客服「简洁回答」的业务要求。`temperature=0.3` 让回答更稳定，因为客服场景准确性优先于创造性。

**Q11：API 调用失败时程序会崩吗？**
A：不会。`llm_client.chat()` 返回 `None`，`main.py` 收到后回复「系统暂时繁忙，请稍后再试」，`agent.py` 也返回兜底话术；命令行版启动前还会自检 `create_client()`，缺 Key 时直接给出配置指引并退出。

## 三、Prompt Engineering

**Q12：System Prompt 里写了哪些关键约束？**
A：三层：①角色设定（电商客服「小智」）；②工作方式（涉及价格/库存/售后必须先调工具，禁止凭记忆编造）；③行为准则（工具失败如实说明、回答 3 句以内、结合上下文理解指代、模拟数据不冒充真实平台）。`main.py` 版本还把整个知识库原文 `build_knowledge_text()` 拼进 Prompt。

**Q13：怎么防止模型编造价格？**
A：靠「约束 + 机制」双保险：Prompt 明令禁止编造，机制上把价格只放在工具返回的数据里，模型不接触就无法凭空给出准确值。测试里问「苹果手机多少钱」，`search_product` 返回 `success=false`，模型回答「店里没有苹果手机」并列出实际商品，而不是编价格。

**Q14：为什么 `agent.py` 的 Prompt 里不直接注入整个商品知识库？**
A：Agent 版本靠工具按需查询，比全量注入更省 token、也更适合商品变多的情况。`main.py` 保留了「知识直接注入 Prompt」的对照实现，正好可以对比两种思路：小规模注入简单，大规模需要按需检索。

## 四、RAG / Embedding / 向量检索（RAG 已实现；神经网络 Embedding 与向量数据库未用，必须如实区分）

**Q15：你的项目用了 RAG 吗？完整链路是什么？**
A：**用了，是轻量 RAG**，在 `rag.py`。链路：把 3 个商品切成 9 块（基础/规格/售后）+ 7 条 FAQ = 16 个知识块 → 中文 bi-gram 分词 → 计算 IDF → 查询和文档都转成 L2 归一化的 TF-IDF 稀疏向量 → 余弦相似度排序取 Top-K → 低于阈值就返回空、强制拒答 → 命中后做父文档扩展 → 片段拼进工具结果交给模型生成回答。`search_knowledge` 工具是它的入口。同时 `main.py` 保留了「知识直接注入 Prompt」的对照实现。

**Q16：为什么用 TF-IDF 而不是神经网络 Embedding？**
A：DeepSeek 官方不提供 Embedding 接口，本地也没有 GPU/向量模型；TF-IDF 零依赖、可解释、每行都能讲清楚，且**它仍是真实向量检索**——查询和文档都转成向量再算夹角，不是关键词匹配。代价是只能捕捉字面/词共现层面的语义，真正的同义泛化（「听歌用的」→「蓝牙耳机」）不如稠密向量。**项目未用神经网络 Embedding 模型**，这是未来升级方向。

**Q17：什么是 Embedding？和你的 TF-IDF 有什么区别？**
A：Embedding 通常指神经网络把文本映射成低维稠密向量，语义相近的文本距离近；TF-IDF 是高维稀疏向量，权重来自词频和逆文档频率。前者能捕捉语义泛化，后者靠词项重合、更透明且不需要模型。（概念了解，项目中未调用 Embedding 接口。）

**Q18：拒答阈值 0.28 是怎么来的？**
A：用标准问答集标定的。我测了一批相关和无关问题：相关问题的 Top1 相似度在 0.29~0.35（「背包防水吗」0.3035、「怎么退货」0.2939），无关问题最高只有 0.257（「以旧换新」误撞了保温杯的「15天换新」）和 0.118（「苹果手机」）。所以把阈值定在 0.28，能保留相关、拦住无关。这也说明阈值必须用评测集调，不能拍脑袋。

**Q19：什么是父文档扩展？为什么需要它？**
A：问「保温杯能保温多久」时，含答案的规格切片分数只有 0.269，会被 0.28 阈值滤掉。所以命中某商品后，我把该商品的其余切片作为「同来源补充」一起带入（总数上限 4 块）。这是 RAG 里常见的 parent-document 技巧：先定位到实体，再补齐该实体的完整上下文，避免答案恰好在被过滤的片段里。

**Q19b：FAQ 为什么要做混合检索？**
A：评测发现「什么时候发货」匹配不到键为「物流」的 FAQ，模型因此拒答了本该能答的问题。修法是 `search_faq` 精确关键词优先、未命中时降级到 RAG 语义检索（限定 FAQ 域，阈值单独标定为 0.15），返回里带 `retrieval` 字段标明是哪种方式。修完该用例通过。

**Q19c：为什么不用 FAISS / Chroma？**
A：只有 16 个文档块，暴力计算余弦相似度微秒级完成，引入向量库只会增加依赖、索引维护和调试成本。商品到几千块时再换，并且届时也应该换成神经网络 Embedding。

## 五、Function Calling / 工具调用

**Q20：工具是怎么告诉大模型「我有哪些能力」的？**
A：`tools.TOOL_SPECS` 是 OpenAI 格式的 JSON Schema 列表，每个工具有 `name`、`description`（什么时候用）、`parameters`（参数与类型）。调用 `chat.completions.create(..., tools=TOOL_SPECS)` 时一起发给模型，模型据此判断该调哪个工具、传什么参数。

**Q21：模型选完工具后，程序做了什么？**
A：模型返回 `message.tool_calls`，程序遍历它，用 `json.loads` 解析参数（解析失败兜底成 `{}`），通过 `TOOL_FUNCTIONS` 映射表找到真正的 Python 函数执行，把结果 `json.dumps` 后以 `{"role": "tool", "tool_call_id": ...}` 回传给模型，模型再生成最终回答。**模型只做决策，数据一定来自函数执行。**

**Q22：怎么保证模型不伪造工具执行结果？**
A：工具结果由程序拼进 messages，模型无法替换；工具统一返回 `success` 字段，失败时返回明确 `error`，Prompt 要求如实告知顾客；`execute_tool` 还会拦截未知工具、参数类型错误和执行异常，返回结构化错误而不是崩溃。Agent 循环最多 3 轮，防止模型反复调用不收敛。

**Q23：12 个工具分别是什么？**
A：商品/知识侧 6 个：`search_product`、`check_stock`、`search_faq`、`recommend_product`、`transfer_to_human`、`search_knowledge`（RAG）；业务侧 6 个：`query_order`、`query_logistics`、`query_refund`、`apply_after_sale`、`place_order`、`advance_after_sale`。每个都在 `tests/test_agent.py`、`tests/test_business.py` 或评测集里验证过意图识别与真实执行。

## 六、Agent 工作流

**Q24：Agent 和普通聊天机器人的本质区别？**
A：聊天机器人是「问 → 答」，答案全靠模型内部知识；Agent 是「问 → 思考 → 调工具 → 看结果 → 再答」，能操作外部数据。我的循环最多 3 轮，属于简化 ReAct（推理 + 行动交替）思路，没有用 LangChain/LangGraph，代码约 100 行，执行过程完全可控。

**Q25：为什么没用 LangChain / LangGraph？**
A：一个 Agent、12 个工具、一个循环，原生 Function Calling 足够，且调试时每一步 messages 都看得见；框架会带来额外抽象和版本兼容成本。面试时能把循环逐行讲清楚，比调用现成框架更能体现理解深度。

## 七、多轮对话

**Q26：大模型本身没有记忆，你怎么实现多轮对话？长对话怎么处理？**
A：每次 API 调用都把完整历史重新传过去：`ConversationMemory` 保存 user/assistant 消息，`agent.run()` 拼成 `system + history + 本轮提问`。三层控制：① `_trim()` 只保留最近 10 轮；② 历史超过 12 条时，`maybe_summarize()` 让模型把最旧 8 条压缩成 150 字摘要，作为长期记忆并入 System Prompt（滚动摘要），而不是粗暴丢弃；③ 摘要调用失败则降级为截断，绝不影响主流程。`MemoryManager` 按 `user_id` 隔离用户，网页版可切换顾客 A/B/C 演示隔离。

**Q27：顾客问完「蓝牙耳机多少钱」再问「有货吗」，系统怎么知道指的是耳机？**
A：第二问发送时带了上一轮历史，Prompt 也要求结合上下文理解指代。但**我不允许模型直接复用历史里的库存数值**：因为下单会真实扣减库存，Prompt 明确要求价格/库存每次都重新调工具。评测第一轮就抓到模型复用了旧数值（多轮用例 M01 未通过），修复后重测通过。这是「上下文记忆」与「实时数据一致性」的取舍。

## 八、异常处理与测试

**Q28：你遇到过哪些实际问题，怎么解决的？**（挑 3 个讲）
A：① Spyder runtime 没有 pip → 改用独立 venv + spyder-kernels；② Windows GBK 编码打印 emoji 报 `UnicodeEncodeError` → 统一 `sys.stdout.reconfigure(encoding="utf-8")`；③ Streamlit 按钮点击后消息要再点一次才显示 → 展示代码在按钮之前，补 `st.rerun()`，并用 `AppTest` 写回归测试。另外还有 402 余额不足、后台重复起 6 个 streamlit 进程导致卡顿，都属于环境/状态问题，用分层验证定位。

**Q29：测试怎么设计的？**
A：6 组共 76 项：`test_scenarios.py`(5)、`test_agent.py`(6)、`test_business.py`(38，含下单/状态机/RAG)、`test_rag.py`(16，纯本地)、`test_memory.py`(9，用假 chat 函数测摘要不花钱)、`test_app_ui.py`(2，`AppTest` 模拟点击)。此外 `evaluate.py` 用 22 条标准问答集做量化评测，输出 `docs/评测报告.md`。本地逻辑测试零成本，API 集成测试每次约 0.001 元。

**Q30：工具调用失败时顾客会看到什么？**
A：工具返回 `success=false` 和具体 `error`，模型据此回答「无法确认 / 没有该商品 / 请核对订单号并联系人工」，绝不编造。`execute_tool` 对未知工具、参数错误也走同一套兜底。

## 九、项目架构与电商业务

**Q31：项目是怎么分层的？为什么这么做？**
A：数据层（JSON，含种子数据与运行时状态）→ 检索/领域层（`rag.py` / `knowledge.py` / `business.py`）→ 工具层（`tools.py`）→ Agent 层（`agent.py`）→ 展示层（`app.py` / `main.py`），配置集中 `config.py`，记忆独立 `memory.py`，评测独立 `tests/evaluate.py`。还有一个关键设计是**职责分离**：价格/库存/订单这类会变化的结构化字段走工具实时查，规格/描述/FAQ 这类静态文本走 RAG，RAG 文档里不写库存，避免检索到过期数据。

**Q32：订单/物流数据是真实平台的吗？**
A：不是，全部是 `data/orders.json` 里的模拟演示数据，每个工具返回值都带 `data_source: "模拟演示数据（非真实电商平台）"`，Prompt 也要求不得声称来自真实平台；README 和界面都做了声明。真实接入需要平台授权和正式 API，那是未来方向。

**Q33：`search_faq` 和 `query_logistics` 都涉及物流，怎么区分？**
A：`search_faq` 回答的是**通用规则**（「一般 1-2 个工作日发货」），`query_logistics` 查的是**某个具体订单的包裹状态**（运输中、华东转运中心、预计送达）。我在 Agent 的 System Prompt 里专门写了这条区分规则，测试也分别覆盖了。

**Q34：如果让你继续做一个月，你优先做什么？**
A：第一是把 TF-IDF 升级为神经网络 Embedding + FAISS/Chroma（当前已有轻量 RAG，缺的是语义泛化能力）；第二是订单与会话写入 SQLite 支持多进程；第三是扩大人工标注评测集、用语义相似度评分替代关键词比对；第四是 API 重试、限流、成本核算与 Docker 部署。这些都在 README 写明了。

## 十、升级版追问（有状态业务 / 评测 / 可观测性）

**Q35：什么叫「有状态」的模拟业务？和之前有什么区别？**
A：初版所有查询都是只读的，订单写死在 JSON 里。升级后 `place_order` 会校验库存、真实扣减、生成新订单并写入 `data/state.json`；`apply_after_sale` 生成申请单并进入状态机「已提交 → 审核通过 → 退款处理中 → 退款完成」，`advance_after_sale` 逐步推进，`query_refund` 会优先读状态机进度。所有状态重启后仍在，侧边栏「重置演示数据」可恢复种子状态。这让 Agent 从「只能查」变成「能办事」。

**Q36：下单后怎么保证不会回答过期库存？**
A：两处：`check_stock` 走 `business.get_stock()` 读实时值；Prompt 明确要求价格/库存每次都重新调工具、不许沿用历史里的旧数值。评测用例 M01 就是专门验证这一点的，首轮失败、修复后通过。

**Q37：你的评测是怎么做的？结果可信吗？**
A：`data/eval_set.json` 有 22 条标准问答，字段含期望工具、期望关键词、禁止词和是否要求拒答；`evaluate.py` 逐条真实跑 Agent，比对 `last_tool_calls` 和回复文本，算出工具选择准确率、事实准确率、拒答正确率、幻觉拦截率，写入 `docs/评测报告.md`。本次实测 22/22。但我会在面试时主动说明局限：样本只有 22 条、关键词比对法覆盖不了等价表述、模型输出有随机性，**这不是生产级准确率**，只是演示系统的回归验证。

**Q38：评测结果不好时你怎么处理？**
A：首轮 19/22，三个失败：①「怎么退货」被误判成要办业务而追问订单号 → 改 Prompt 区分「咨询通用规则」与「办理具体业务」；②「什么时候发货」没调到 FAQ → 模型规则修正后仍因关键词不匹配失败，于是给 FAQ 加语义检索兜底；③ 多轮追问库存复用了旧值 → 强制每次重查工具。修完重测 22/22。**没有改评分标准去刷分**，都是修根因。

**Q39：网页侧边栏展示了什么？为什么做这个？**
